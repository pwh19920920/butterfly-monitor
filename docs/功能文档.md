# 功能文档


---

## 1. 系统功能概览


| 功能模块 | 说明 |
|---|---|
| 监控任务管理 | 配置数据采集任务（数据库 SQL / URL HTTP / 外部推送），设定采集周期与指令 |
| 数据源管理 | 管理被监控的 MySQL / MongoDB 数据源，密码加密存储 |
| 监控分组 | 树形依赖分组，用于关联预警链路 |
| 监控面板 | 对接 Grafana 自动创建/管理监控大盘与 panel |
| 告警规则 | 为任务配置阈值规则（百分比/绝对值/样本差值，5 种比较，Or/And 组合，生效时段，分级） |
| 告警配置 | 全局 KV 配置（报警间隔、首次延迟、通知模板、告警中心 key、样本生成参数） |
| 告警分组 | 管理告警接收人分组与成员 |
| 告警通道 | 管理邮件 / 企业微信通知通道，支持测试发送 |
| 告警事件 | 告警事件查询、处理（误报标定）、完成（恢复通知） |
| 首页统计 | 任务/事件/面板/数据源数量聚合 |
| 健康检查 | 探活接口 |

### 1.1 核心业务链路

```
指标采集(dataCollect) → 样本生成(dataSampling) → 规则检测(alertCheck) → 事件通知(eventCheck)
```

四个定时任务由 XXL-JOB 调度，cron 在 admin 端配置：

- **dataCollect**：定时从数据源采集指标写入 VictoriaMetrics，同时写未来 8 天同时刻样本原料点。
- **dataSampling**：按窗口生成样本（去除最大值最小值取平均值），写入平滑基线指标 `{taskKey}_sample`。
- **alertCheck**：比对实时均值与平滑基线均值，命中并持续达阈值生成告警事件。
- **eventCheck**：到期事件经模板渲染，通过邮件/企业微信/钉钉外发。

### 1.2 告警生命周期

```
规则命中(异常持续) → 生成事件(Pending) → 到期外发(firing) → 人工处理 → 完成(恢复通知 resolved)
                         ↑ 失败/误报可标 Ignore
```

- **Pending**（待处理）：事件已生成，等待 `NextAlertTime` 到期外发。
- **Processing**（处理中）：人工介入处理，暂停检测。
- **Complete**（已完成）：处理完成，若曾告警则发恢复通知。
- **Ignore**（已忽略）：误报标定，不外发。

## 3. 功能模块详解

### 3.1 监控任务

监控任务是系统的核心实体，一条任务定义了"采集什么、怎么采集、多久采集、告警规则是什么"。

**任务类型**（`TaskType`）：

| 值 | 类型 | 说明 |
|---|---|---|
| 1 | Database（数据库） | `Command` 是 SQL，`ExecParams` 含 `databaseId`，从连接池取对应数据源执行 |
| 2 | URL | `Command` 是 URL 模板，`ExecParams` 含 `resultFieldPath`，HTTP GET 探测取 JSON 路径值 |

**关键字段**：
- `TaskKey`：任务标识，**同时作为 VictoriaMetrics 指标名**，需全局唯一。
- `TimeSpan`：窗口前进间隔（秒），决定采集周期。
- `StepSpan`：查询区间宽度（秒）。
- `Command`：执行指令（URL 或 SQL 模板，支持 `text/template` + `sprig` 渲染，可引用 `endTime`/`beginTime`/`startTime`/`startTimeMilli`/`endTimeMilli`/`beginTimeMilli`）。
- `ExecParams`：执行参数 JSON。
- `TaskStatus`/`AlertStatus`/`Sampled`：任务开关/告警开关/样本展示开关。
- `MonitorGroup`：依赖分组（逗号分隔 groupId，关联预警用）。
- `Labels`：标签 JSON（告警收敛中心扩展参数）。

**采集周期机制**：分片查询条件 `date_add(now(), interval -time_span second) >= pre_execute_time`，即距上次执行已超过一个 `TimeSpan` 才到下次采集点。`dataCollect` Job 模式只采集最近一个窗口。

**样本机制**：采集时**无条件**同步写未来 8 天同时刻样本原料点（指标 `{taskKey}_sampling`，标签 `day=1..8`），`dataSampling` 按窗口去除最大最小后取均值、生成平滑基线写入新指标 `{taskKey}_sample`，`alertCheck` 用 `avg({taskKey}_sample)` 与 `avg({taskKey})` 实时均值做对比。**`Sampled` 开关只控制 Grafana 面板是否展示样本对比线，不影响采集与样本生成**——样本数据始终采集与生成，`Sampled` 决定的是"是否在面板上展示"。

### 3.2 数据源

数据源是被监控的数据库实例配置，密码密文存储（DES-CBC + 随机 8 位盐）。

**数据源类型**（`DataSourceType`）：

| 值 | 类型 | handler | `task.Command` 语义 |
|---|---|---|---|
| 0 | MysqlOld | `DatabaseMysqlHandler` | SQL，`db.Raw().Scan(&float64)` |
| 1 | Mongo | `DatabaseMongoHandler` | Extended JSON 聚合管道 |
| 2 | Mysql | `DatabaseMysqlHandler` | SQL |

**连接池动态注册**：`CommonMapApplication` 启动后台 goroutine 每分钟增量扫描 `t_monitor_database`，对每条调 `databaseHandler.NewInstance` 建连，成功的放进 `databaseMap[id]`，注入 `CommandDataBaseHandler`。新增/修改的数据源最多 1 分钟后生效。

### 3.3 监控分组

树形依赖分组，用于"关联预警"链路。`Route` 字段形如 `/1/2/3/`，`Parent` 为上级 id。修改分组时级联更新所有子节点 Route。

**关联预警**：`eventCheck` 的 `getEventRelationParams` 按 `task.MonitorGroup` 取 `MonitorGroup.Route`，`LastIndex(route, "/")` 去掉最后一节，`Split(route[0:lastIndex], "/")` 得上游 groupId 列表，从各组 pending events 取关联 task name，串成 "A -> B -> C" 链路关系名放进通知模板。

### 3.4 监控面板

对接 Grafana，自动创建/管理大盘与 panel。

- **创建面板**：调 `grafanaHandler.CreateDashboard(name)`，从响应回填 `Url/Slug/Uid/BoardId`。
- **panel 标识**：以 `panel.Description == taskKey` 为锚点做增删改。每个 task 对应一个 timeseries panel，Grafana 数据源为 Prometheus（指向 VictoriaMetrics），target A 用 MetricsQL 查 `avg({taskKey})`，`Sampled=Open` 时加 target B 查 `avg({taskKey}_sample)` 做样本对比。
- **三段式同步**：修改任务时计算 dashboard 新增/删除/交集三集合，`ModifyDashBoardPanel` 同步 Grafana：交集只改 title、删除匹配 panel、新增 panel。
- **自动布局**：`sortPanels` 3 列网格（每格 `8×8`）。
- **排序**：`/api/monitor/dashboard/taskSort` 批量改排序后，`ReSortDashboard` 按 taskId 顺序重建 panels。

### 3.5 告警规则

每个任务一条告警规则 `MonitorTaskAlert`，核心是 `Params`（规则 JSON）。

**规则结构**：
- 组间关系 `Relation`：1=Or（一组命中即整体命中）、2=And（全命中才命中）。
- 组内规则 `Rules`：每条含 `ValueType`（比较值类型）、`Value`（阈值）、`CompareType`（比较方式）。
- 生效时段 `EffectTimes`：`[startHH:mm:ss, endHH:mm:ss]`，不在时段内跳过该组。
- 事件等级 `Level`：nil 默认 Critical。

**三种比较值类型**：

| ValueType | 值 | 含义 |
|---|---|---|
| Percent | 1 | 样本百分比：`(real - sample) * 100 / sample` |
| AbsoluteValue | 2 | 绝对值（差值）：`real - sample` |
| Value | 3 | 样本差值：不依赖样本，直接比较实时值 |

**五种比较方式**：

| CompareType | 值 | 中文 | 差值模式 | 绝对值模式 |
|---|---|---|---|---|
| Gt | 1 | 超出 | `diff > value` | `real > value` |
| Lt | 2 | 低于 | `diff < -value` | `real < value` |
| Eq | 3 | 等于 | `diff == value` | `real == value` |
| Egt | 4 | 超出或等于 | `diff >= value` | `real >= value` |
| Elt | 5 | 低于或等于 | `diff <= -value` | `real <= value` |

**告警等级**（`MonitorAlertCheckParamsLevelType`）：

| 常量 | 值 | 中文(loadLevel) | 英文(transferLevel) |
|---|---|---|---|
| Normal | -1 | 低级（default） | Low |
| Critical | 0 | 严重 | Critical |
| High | 1 | 高级 | High |
| Medium | 2 | 中级 | Medium |
| Low | 3 | 低级 | Low |

**规则命中流程**（`alertCheck`）：
1. 时间倒退窗口 `[now-2*TimeSpan, now-TimeSpan)` 查平滑基线均值 `avg({taskKey}_sample)` 与实时均值 `avg({taskKey})`。
2. `checkForParam` 校验：实时值缺失即异常（Low 级）；否则按规则组校验。
3. 三个分支：
   - **未命中** → 恢复正常（`ModifyForNormal`），pending events 标 Ignore，同步发恢复通知（`DoNotifyRecover`，status=`resolved`）。
   - **命中但未超 Duration** → 置 Pending（`ModifyByPending`），冻结 `FirstFlagTime` 作持续起点。
   - **命中且超 Duration** → 置 Firing（`ModifyByFiring`），创建/更新事件（`DealStatus=Pending`、`NextAlertTime=now+FirstDelay`、`EventLevel=level`）。

**Alert 状态机**：

| AlertStatus | 值 | 含义 |
|---|---|---|
| Normal | 1 | 正常 |
| Pending | 2 | 出现异常（待观察，等待 Duration） |
| Firing | 3 | 达到报警条件（正在报警） |

### 3.6 告警配置

通用 KV 配置表，运行期装配成 `AlertConfObject`。关键配置项见 §2.6。

**配置动态装配**：`Cover2AlertConf` 用独立 viper 实例，设默认值（`alert.firstDelay=60`、`alert.alertSpan=600`），再以 `alert.<ConfKey>=<ConfVal>` 逐条覆盖，最后 `Unmarshal`。

**NextAlertTime 握手机制**：
- `alertCheck` 建事件时 `NextAlertTime = now + FirstDelay`（首次延迟 60s）。
- `eventCheck` 发送成功后 `NextAlertTime = now + AlertSpan`（默认 600s）。
- `FindEventJob` 扫描条件 `now() >= next_alert_time`，实现报警收敛/频次控制。

### 3.7 告警分组

管理告警接收人分组与成员（多对多中间表 `t_alert_group_user`）。告警时按 `alert.AlertGroups` 解析出分组，再按分组取用户列表，最后按通道发送。

### 3.8 告警通道

| 通道 | Handler | 参数 | 发送方式 |
|---|---|---|---|
| 邮件 | `ChannelEmailHandler` | `{Host, Port, SSL, Username, Password}` | SMTP/SMTPS，主题"报警提醒"写死，纯文本正文 |
| 企业微信 | `ChannelWechatHandler` | `{Addr}`（机器人 webhook） | POST `{"msgtype":"markdown","markdown":{"content": message}}` |
| 告警收敛中心 | `AlertMgtHandler`（不走 ChannelHandler） | `business.AlertMgt` 地址 | 直接 HTTP POST，要求响应 `code==0` |

通道 handler 不做模板渲染，`message` 由 `eventCheck` 的 `RenderTemplate` 渲染后传入。模板源是 `t_alert_conf.template` 配置项，用 `text/template`（无 sprig），按 `items` 切片迭代渲染多条。

**告警中心推送**（`eventCheck` 的 `asyncNoticeAlertSys`）：
- 每 event 一个 goroutine（25s 超时）。
- 依赖 `task.Labels` 非空且包含 `AlertMgmtKey` 所列 labelKey，否则静默跳过。
- payload：`{source="Spider", status="firing", level, name, labels, alert_id, fire_event_id, metric_charts, markdown.content=event.AlertMsg}`。
- level 优先级：`labels["alert_level"]` > `transferLevel(event.EventLevel)` > `defaultAlertLevel(Critical)`。

### 3.9 告警事件

事件状态机（`DealStatus`）：

| 值 | 状态 | 说明 |
|---|---|---|
| 1 | Pending（待处理） | 已生成，等待到期外发 |
| 2 | Processing（处理中） | 人工介入，暂停检测 |
| 3 | Complete（已完成） | 处理完成，曾告警则发恢复通知 |
| 4 | Ignore（已忽略） | 误报标定 |

**事件处理闭环**：
- `DealEvent`（处理）：余者标误报 → 当前事件置 Processing。
- `CompleteEvent`（完成）：曾告警则 `DoNotifyRecover` → 状态置 Normal。
- 恢复回调在判定恢复当轮立即下发（`alertCheck` 未命中分支同步触发），不等 `NextAlertTime`。

### 3.10 首页统计

`/api/monitor/homeCount` 聚合返回 TaskCount / EventCount / DashboardCount / DatabaseCount，免登录。

## 5. 定时任务

四个定时任务由 XXL-JOB 调度，cron 在 admin 端配置，不在代码中。

| 任务名 | 功能 | 分片 | 关键参数 |
|---|---|---|---|
| `dataCollect` | 采集指标写 VictoriaMetrics + 写未来 8 天样本原料点 | `mod(id,Total)=Index` | `TimeSpan`/`StepSpan`/`TaskType`/`Command`/`ExecParams` |
| `dataSampling` | 按窗口去最大最小取均值，生成平滑基线 `{taskKey}_sample` | 分片 + `id>lastId` 游标分页 | `SimplePageSize`(50)/`SimpleMaxSecond`(600s) |
| `alertCheck` | 比对实时均值与平滑基线均值，命中生成事件 | `mod(id,Total)=Index`（按 alert.id） | `Duration`/`Params`/`FirstDelay`(60s) |
| `eventCheck` | 到期事件模板渲染外发 + 推送告警中心 | 不分片，全量扫描到期事件 | `AlertSpan`(600s)/`Template`/`AlertMgmtKey` |

**分片参数** `BroadcastIndex`/`BroadcastTotal` 由 XXL-JOB 调度中心下发，支持多 executor 实例水平扩展，同一任务按 `mod(id, Total)` 哈希到不同分片，避免重复执行。

## 6. 外部系统集成

### 6.1 告警收敛中心

- 地址：`business.alertMgt`（各 profile 不同，测试 `alert-mgmt.test.weicai.com.cn/alert/code`，生产 `alert-mgmt.weicai.com.cn/alert/code`）。
- 触发点：`eventCheck` 异步 `DoNotifyAlert`（firing）；`alertCheck` 未命中同步 `DoNotifyRecover`（resolved）。
- 门控：`task.Labels` 非空且包含 `AlertMgmtKey` 所列 labelKey，否则静默跳过。
- payload：`source=Spider`、`status=firing/resolved`、`level`、`name`、`labels`、`alert_id`、`fire_event_id`、`metric_charts`（面板名→URL）、`markdown.content=告警正文`。
- 成功判定：响应 `code==0`。

### 6.2 Grafana

- 地址：`grafana.addr`（各 profile 不同）。
- 集成点：监控任务增删改同步操作 Grafana 面板与 panel；面板查询时 Url 前拼 `Grafana.Addr`。
- panel 查询：Grafana 数据源为 Prometheus（指向 VictoriaMetrics），用 MetricsQL。实时点指标=`{taskKey}` 查 `avg({taskKey})`；样本对比线（`Sampled=Open` 时）查平滑基线指标 `{taskKey}_sample` 的 `avg({taskKey}_sample)`。

### 6.3 XXL-JOB

- 地址：`xxl.serverAddr`。
- 执行器：取本机非回环 IPv4 作为 ExecutorIp，端口与 gin `serverAddr` 一致，RegistryKey=`server.serverName`。
- 注册路由：`POST /run`、`POST /kill`、`POST /log`。

### 6.4 数据源（被监控）

- MySQL：gorm + mysql driver，连接池 idle10/open100/life3600s。
- MongoDB：mongo-driver，`SetMaxPoolSize(5)`，聚合管道查询。

## 7. 使用流程示例

### 7.1 新增一个数据库监控任务

1. **数据源管理**：`POST /api/monitor/database` 创建 MySQL 数据源（填库名/账号/密码/地址/类型），系统验证连通性并加密密码。
2. **监控分组**（可选）：`POST /api/monitor/group` 创建依赖分组（树形），用于关联预警。
3. **监控面板**：`POST /api/monitor/dashboard` 创建 Grafana 面板。
4. **创建任务**：`POST /api/monitor/task`，填 `TaskKey`（唯一）、`TaskName`、`TimeSpan`/`StepSpan`、`Command`（SQL）、`TaskType=1`、`ExecParams={"databaseId": <id>}`、关联 dashboardIds、`MonitorGroup`、告警规则 `Params`。系统校验 TaskKey 唯一、在 Grafana 加 panel、事务保存。
5. 启用任务：`PUT /api/monitor/task/taskStatus/:id/1` 开启；`PUT /api/monitor/task/alertStatus/:id/1` 开启告警；`PUT /api/monitor/task/sampled/:id/1` 开启样本对比线展示（不影响采集与生成，仅控制 Grafana 面板是否叠加样本曲线）。
6. XXL-JOB admin 配置 `dataCollect`/`dataSampling`/`alertCheck`/`eventCheck` 四个任务的 cron 与分片。

### 7.2 配置告警通知

1. **告警通道**：`POST /api/alert/channel` 创建邮件/企业微信通道（填 Host/Port/SSL/Username/Password 或 webhook Addr），系统测试发送验证。
2. **告警分组**：`POST /api/alert/group` 创建分组并绑定用户（用户来自 `t_sys_user`）。
3. **告警配置**：`POST /api/alert/conf` 配置 `alertSpan`/`firstDelay`/`template`/`alertMgmtKey` 等。
4. 创建/修改任务时在告警规则中填 `AlertGroups`（逗号分隔 group id）和 `AlertChannels`（逗号分隔 channel id）。

### 7.3 处理告警事件

1. 查询事件：`GET /api/monitor/task/event`。
2. 处理（人工介入）：`POST /api/monitor/task/event/deal/:id`，系统把同 task 其余 pending events 标为误报，当前事件置 Processing。
3. 完成：`POST /api/monitor/task/event/complete/:id`，若该事件曾告警过，系统自动向告警中心发恢复通知（resolved），事件置 Complete。

## 8. 常见问题

**Q：新增数据源后任务多久能用到？**
A：最多 1 分钟。`initDatabaseConnect` 后台 goroutine 每分钟增量扫描 `t_monitor_database` 建连注入连接池。在此之前 DB 类型任务执行会报 `dbMap is not contain <id>`。

**Q：告警为什么不外发？**
A：检查几项：
1. 事件是否到期：`FindEventJob` 条件 `now() >= next_alert_time`，未到期不外发。
2. 通道是否配置且测试通过：`AlertChannels` 是否填了有效 channel id。
3. 分组是否有成员：`AlertGroups` 对应分组下是否有用户。
4. 告警中心是否推送：`AlertMgmtKey` 是否配置、`task.Labels` 是否非空且包含所列 labelKey（否则静默跳过）。
5. 任务/告警开关是否开启：`TaskStatus`/`AlertStatus` 是否为 1。

**Q：告警多久发一次？**
A：首次 `alertCheck` 建事件后 `NextAlertTime = now + FirstDelay`（默认 60s）；`eventCheck` 发送成功后 `NextAlertTime = now + AlertSpan`（默认 600s=10 分钟）。可在 `t_alert_conf` 调整, 告警成功后记录告警次数, 下一次告警的时间2 * AlertSpan, 直至最大30分钟后不再升级。

**Q：恢复通知什么时候发？**
A：`alertCheck` 判定未命中（恢复正常）的当轮立即同步发 `DoNotifyRecover`（resolved），不等 `NextAlertTime`。前提是该事件曾告警过（存在 `PreAlertTime`）。

**Q：样本基线是什么？**
A：采集时同步写未来 8 天同时刻的样本原料点（`{taskKey}_sampling`，标签 `day=1..8`），`dataSampling` 按窗口去除值最大/最小两个点后取均值，生成平滑基线写入新指标 `{taskKey}_sample`（只写不删，样本原料保留）。`alertCheck` 用 `avg({taskKey}_sample)` 与实时均值 `avg({taskKey})` 比对。注意样本原料**始终采集**，`Sampled` 开关只控制 Grafana 面板是否展示样本对比线，不控制采集与生成。

**Q：`Sampled`（样本展示开关）开了/关了有什么影响？**
A：`Sampled=Open` 时，Grafana 面板会在实时曲线基础上叠加一条样本对比线（target B 查平滑基线 `{taskKey}_sample` 的 `avg({taskKey}_sample)`）；`Sampled=Close` 时不展示该对比线。**无论开关如何，样本原料都会被采集、平滑基线都会由 `dataSampling` 生成**——开关只影响 Grafana 面板展示，不影响 VictoriaMetrics 中样本原料 `{taskKey}_sampling` 的写入与 `{taskKey}_sample` 的生成逻辑。

**Q：多实例部署如何避免重复执行？**
A：所有定时任务按 `mod(id, shardTotal) = shardIndex` 分片，分片参数由 XXL-JOB 调度中心下发。多实例各取不同分片，同一任务不会重复执行。`eventCheck` 不分片，建议单机或轮询路由。

**Q：TaskKey 有什么用？**
A：`TaskKey` 是任务唯一标识，**同时作为 VictoriaMetrics 指标名**（实时点指标=`{taskKey}`，样本原料指标=`{taskKey}_sampling`，平滑基线指标=`{taskKey}_sample`），也是 Grafana panel 的 `Description` 锚点。修改时原则上不改 TaskKey。
